## Headline (holdout_1m, BACKHAUL_DEGRADATION, n = 53)

| | median TTD | p90 | within 5 min | false alerts per 100 healthy link-days |
|---|---|---|---|---|
| before: per-cell rules (published metric a) | 562 s | 810 s | 7.5 % | 135 (per-cell KPI alerts grouped per link) |
| after: per-cell + collective, first of | **332 s** | **467 s** | **17.0 %** | +0 collective (0 in 195.7 link-days; 95 % upper bound about 1.5) |

The median gain is 190 s (about 3.2 min). Small links (≤ 6 cells, n = 22) gain about as much as large ones
(n = 31). Most faults are still outside the 5-minute SLA, and about 120 s of each collective TTD is the 120 s
watermark. Generator noise is nearly independent across cells, so these gains and the zero false-alarm count are
an upper bound.

## Problems found during the step (all fixed, none touched the detector)

1. **Result fetch dropped chunks.** The first calibration sweep read only the first result chunk (101,651 of
   381,832 link-minutes), so minutes were missing and persistence broke. Fix: page through every external link and
   check the row count against the statement's `total_row_count`. The sweep was re-run before the freeze; the
   committed `01_calibration.md` is the complete one. The incomplete sweep's choice was never committed or used.
2. **Undetected incidents read as detected at 0 s.** `eval_incident_detection.impact_ttd_s` is 0, not NULL, when
   nothing was detected (`greatest(NULL, 0)`). The *before* lookup used it as-is, so INC-00204 (holdout) and two dev
   incidents counted as per-cell detections at 0 s. Fix: use `impact_detected`. The holdout was re-scored once from
   its stored detections (`03b`, no holdout data re-read): the detections are identical, but the combined *after* arm changed with the *before* arm: after median 331 -> 332 s, p90 461.2 -> 467.1 s, within 5 min 18.9 % -> 17.0 %; before 559 -> 562 s, 807.6 -> 810.3 s, 9.4 -> 7.5 %; collective-alone and false alarms unchanged. The published `eval_ttd_summary` medians still include
   these as 0 s (1 holdout and 4 history_1m incidents). That is reported, not changed.
3. **A retried INSERT landed twice** (dev reading, table versions 7 and 8). The write is now an idempotent `MERGE`
   on `(reading, detection_id)`. Dev was re-scored, and the holdout's single write (version 5) was unaffected.

## Published step 2-5 results: before vs after (05_no_change.md)

No pre-step-6 snapshot of the published tables was taken. The **before** reference is therefore the numbers committed in
evidence/step2..4: every committed `(query, output table)` pair in the headline files is re-run and compared row by row,
rendered by the function that wrote it. The **after** reference for the future is a deterministic `sha2` content hash
of each of the 89 published result tables (netmon_eval / netmon_rca / netmon_genai, including the `_pr5` pre-fix
copies), with its `last_altered`. None was altered since step 6 began (the latest change is 2026-11-06 09:45 UTC).

Replay: **54 tables identical**, and **10 with every committed row unchanged**, plus rows of runs that were added after
that file was captured (the step-2 files predate `history_1m` / `holdout_1m`). **5 differ**, none because of step 6:
- `step3/07_pr3_review_notes.md`, two tables: captured before the PR #6 alarm fix. They are **identical to the pre-fix
  `_pr5` snapshot tables**, i.e. the numbers PR #6 superseded, as documented in `step3/08_alarm_id_fix.md`.
- `step2/03_row_counts.md` "All pipeline tables", `step2/02_expectations.md` "Quarantine sample", and
  `step2/05_time_to_detect.md` "late records": whole-table counts, a `LIMIT` sample and cumulative totals that grow with
  every later generator run. They are not result metrics.

Not replayable: the system / event-log queries are skipped and listed. Step 5's headline is the Genie benchmark, answers
of a live LLM in evidence/step5/02*, so there is no table to compare; the serving views it reads sit on the hashed tables.

## C1: poisoned Genie answer

`tests/test_no_ground_truth_surface.py` now posts to `POST /api/genie/ask` with a `FakeGenie` whose answer carries
ground truth in its `sql`, `text`, `description` and result fields, one field at a time and all together:
- **with** an eval table name (`netmon_eval` / `eval_ttd_summary`);
- **without** one: label columns (`fault_type`, `is_censored`, `root_element_id`, `root_cause_*`, `event_class`) and
  fault-class labels (`BACKHAUL_DEGRADATION`, `SITE_POWER_OUTAGE`, `TRAFFIC_SURGE`).

Before the fix the app returned such answers unchanged, including the `fault_type` label column.
`safety.scrub_genie_answer` now:
- drops label columns from Genie result tables;
- withholds the whole answer when it refers to data outside the `netmon_noc` serving views, names a ground-truth label
  column, or carries a fault-class value whose SQL does not read `incident_ai_summary.fault_hypothesis`, the assistant's
  operational guess and the only serving column with such values.

Legitimate answers still pass (tested): sites down, the assistant's hypothesis, prose such as "backhaul degradation",
and alarms with `severity`. The fix is code only. The deployed app picks it up after the next bundle deploy + run
(`docs/topology_app.md`). It was not redeployed from this branch, because a bundle deploy also redeploys the pipeline,
jobs, serving endpoint and Genie space.
