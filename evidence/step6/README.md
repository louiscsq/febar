## Headline (holdout_1m, BACKHAUL_DEGRADATION, n = 53)

| | median TTD | p90 | within 5 min | false alerts per 100 healthy link-days |
|---|---|---|---|---|
| before: per-cell rules (published metric a) | 562 s | 810 s | 7.5 % | 135 (per-cell KPI alerts grouped per link) |
| after: per-cell + collective, first of | **332 s** | **467 s** | **17.0 %** | +0 collective (0 in 195.7 link-days; 95 % upper bound about 1.5) |

The median gain is 190 s (about 3.2 min). Small links (≤ 6 cells, n = 22) gain about as much as large ones
(n = 31). Most faults are still outside the 5-minute SLA, and about 120 s of each collective TTD is the 120 s
watermark. Generator noise is nearly independent across cells, so these gains and the zero false-alarm count are
an upper bound.

## Problems found during the step (all fixed, none touched the detector)

1. **Result fetch dropped chunks.** The first calibration sweep read only the first result chunk (101,651 of
   381,832 link-minutes), so minutes were missing and persistence broke. Fix: page through every external link and
   check the row count against the statement's `total_row_count`. The sweep was re-run before the freeze; the
   committed `01_calibration.md` is the complete one. The incomplete sweep's choice was never committed or used.
2. **Undetected incidents read as detected at 0 s.** `eval_incident_detection.impact_ttd_s` is 0, not NULL, when
   nothing was detected (`greatest(NULL, 0)`). The *before* lookup used it as-is, so INC-00204 (holdout) and two dev
   incidents counted as per-cell detections at 0 s. Fix: use `impact_detected`. The holdout was re-scored once from
   its stored detections (`03b`, no holdout data re-read). The published `eval_ttd_summary` medians still include
   these as 0 s (1 holdout and 4 history_1m incidents). That is reported, not changed.
3. **A retried INSERT landed twice** (dev reading, table versions 7 and 8). The write is now an idempotent `MERGE`
   on `(reading, detection_id)`. Dev was re-scored, and the holdout's single write (version 5) was unaffected.

## C1: poisoned Genie answer

`tests/test_no_ground_truth_surface.py` now posts to `POST /api/genie/ask` with a `FakeGenie` whose answer names
`netmon_eval` / `eval_ttd_summary` in its `sql`, `text`, `description` and result fields, one field at a time and
all together. Before the fix the app returned that answer unchanged, including the `fault_type` label column. Now
`safety.scrub_genie_answer` drops label columns from Genie result tables and withholds the whole answer when any part
of it refers to data outside the `netmon_noc` serving views. The fix is in the code only; the deployed app was not
redeployed in this step.
